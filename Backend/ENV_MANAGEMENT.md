# Environment management for MonitorClient v1.5 backend

The application reads database settings from **environment variables**, not directly
from a `.env` file. A conventional `.env` file will **not** be loaded by PHP unless
you explicitly configure a loader. Never commit database passwords to Git.

## 1. Apache (web requests)

On the standard Ubuntu/Apache mod_php deployment, the DB settings live at:

```text
/etc/monitoring/apache-db.conf
```

This is a root-owned, mode-600 Apache include, normally generated by
`sudo bash Backend/setup_database_access.sh`.

Expected format (do **not** put the real password in documentation):

```apache
SetEnv MONITOR_DB_HOST "localhost"
SetEnv MONITOR_DB_NAME "monitoring_db"
SetEnv MONITOR_DB_USER "monitoring_app"
SetEnv MONITOR_DB_PASSWORD "<secret stored on the server>"
```

The site config `/etc/apache2/sites-available/mybackend.conf` must include:

```apache
IncludeOptional /etc/monitoring/apache-db.conf
```

Check **without printing credentials**:

```bash
sudo test -s /etc/monitoring/apache-db.conf && echo "Config exists"
sudo stat -c '%U %a %n' /etc/monitoring/apache-db.conf
sudo grep -E '^SetEnv MONITOR_DB_(HOST|USER|NAME) ' /etc/monitoring/apache-db.conf
sudo grep -Eq '^SetEnv MONITOR_DB_PASSWORD ' /etc/monitoring/apache-db.conf && echo "Password entry exists"
sudo apache2ctl configtest
```

After changing Apache directives, reload Apache:

```bash
sudo apache2ctl configtest && sudo systemctl reload apache2
```

Do **not** change the `MONITOR_DB_PASSWORD` value without updating the corresponding
MySQL user's password. The provisioning script generates a new random password,
updates `monitoring_app@localhost`, installs the matching Apache configuration,
and reloads Apache. Re-running it **rotates** the DB account password; use only
when the config is missing/broken and after confirming the existing MySQL setup.
The script does not drop or rebuild the monitoring database.

For custom PHP-FPM deployments, configure the same variables in the PHP-FPM pool
or service environment instead of Apache `SetEnv`.

## 2. Terminal (PHP CLI commands)

Apache `SetEnv` directives **do not automatically propagate** to your SSH shell.
`MONITOR_DB_PASSWORD=""` is invalid: the application requires a nonempty value.

From the repository checkout on the server:

```bash
cd /var/monitor
git pull --ff-only origin main

# Install a root-owned copy: never execute web-writable source as root.
sudo install -o root -g root -m 700 Backend/with_database_env.py /usr/local/sbin/monitor-with-db-env

sudo /usr/local/sbin/monitor-with-db-env \
    php Backend/recover_web_login.php --list-admins

sudo /usr/local/sbin/monitor-with-db-env \
    php Backend/diagnose_user_directory.php
```

The installed `monitor-with-db-env` utility reads the root-owned Apache include, extracts only
`MONITOR_DB_HOST`, `MONITOR_DB_USER`, `MONITOR_DB_PASSWORD` and
`MONITOR_DB_NAME` without printing them, then drops root privileges to the
invoking sudo user before launching PHP. The settings last for **that command
only**. No separate `.env` file is required. Keep the installed utility
root-owned and **reinstall it only after reviewing updates** to its source.

To recover an administrator, first list User Nos, then use the secure prompt:

```bash
sudo /usr/local/sbin/monitor-with-db-env --prompt-recovery-password \
    php Backend/recover_web_login.php --reset-user-no=ACTUAL_NUMBER
```

Use the User No shown by `--list-admins`, not the database ID. The wrapper
asks for the new password twice, passing it to PHP without putting it in command
arguments, Git history or source files. See [LOGIN_RECOVERY.md](LOGIN_RECOVERY.md).

## 3. User No directory and LAN access

In the latest backend, direct private-LAN clients can request the directory,
including admin accounts, without a separate enrollment flag. For example:

```bash
curl --fail-with-body -sS -H 'Content-Type: application/json' \
  -d '{"action":"directory"}' http://SERVER_LAN_IP:8924/client_auth.php
```

Use HTTPS port 8925 with the trusted CA when available. Do not make the
HTTP port public. Reverse proxies and non-LAN access have separate explicit
restrictions. `MONITOR_DISABLE_USER_NO_ENROLL=1` forces directory/enrollment
off, while `MONITOR_ENABLE_USER_NO_ENROLL=1` bypasses the LAN gate and
therefore must only be set behind an appropriate firewall/VPN. The selection
feature uses User No alone and is not a strong authentication mechanism.
